# Security review — 2026-07 (verification record)

An external review raised 9 findings (2×P0, 5×P1, 2×P2) plus documentation items. Every
finding was **verified against the code before any fix** — the two P0s and the deadlock were
reproduced, not merely reasoned about. This file is the durable record; the fixes shipped in
**v0.8.1**.

## Verdicts

| # | Finding | Verdict | Evidence |
| :-- | :-- | :-- | :-- |
| **P0-1** | Stored XSS via lesson/contributor labels → signing-key theft | **Confirmed** | 3 of 6 `innerHTML` sites interpolated untrusted `label` (`web/rulegarden/app.js`); labels arrive from imported/peer packs; private seed lives in same-origin IndexedDB |
| **P0-2** | Non-canonical hypervector panics the engine | **Confirmed — reproduced** | `panic: index out of range [10000] with length 10000` at `addBits` ← `Pack.Memory` ← decoded pack JSON; `hvFromHex` never masked the final word's excess 48 bits |

| **P1-2** | Opposite-direction concurrent `Merge` deadlocks | **Confirmed** | `other.mu.RLock()` then `am.mu.Lock()` — receiver-relative order, not global; the comment both claimed "cannot deadlock" and told callers to serialize |

## Two items the review under-stated

1. **`engine.Version = "0.3.0-dev"` is inside signed bytes.** `EngineVersion` is written into
   `DecisionCertificate.CanonicalBytes()`, so every issued receipt *attested* "engine
   0.3.0-dev" while the engine was v0.8.0 — a false provenance claim in a signed artifact,
   not a docs nit. (Verification of *existing* receipts is unaffected: each cert carries its
   own `EngineVersion` field; only newly issued certs change.)
2. **P1-3 + P1-4 compose against the headline guarantee.** The matrix is a many-to-one
   majority vote and labels are attacker-controlled, so a crafted pack can plausibly produce
   two worlds with equal `Hash()` but different bound vectors — which a later `Forget` would
   expose as divergence, attacking "same pack ⇒ bit-identical world." Flagged as a
   composition risk (not a built PoC); the complete-fingerprint fix (P1-3) closes it.

## Root-cause note (kept honest)

The XSS was **documented rather than removed**: the README's "a game identity, not a valuable
credential" caveat was written, then registry import and peer sync — the very features that
turn that caveat into a live key-theft path — were shipped on top of it. Lesson: "stated
plainly in the README" is not a substitute for a fix. The deadlock has the same shape — prose
asserting a safety the code did not provide.

## Addendum (2026-08): P1-4 structural fix shipped in v0.9.0

v0.8.1 mitigated P1-4 at the import boundary (`validateLessonPackContent` re-derives the
bound vector from the label and refuses mismatches) but left the label as the machine-
readable carrier of meaning — the deferred follow-up named in the 0.8.1 changelog. v0.9.0
retires that mechanism:

- Lesson meaning is now a first-class **sem record** (canonical JSON) on the engine ledger
  and pack wire, covered by pack signatures (canonical form v2; packs without sems keep
  their exact v1 bytes, so pre-existing signatures verify unchanged — pinned by the
  committed `engine/testdata/signed_pack_v1.json` fixture), hashed by fingerprints (the
  P1-3 rule: sem is future-relevant state), compared by merge collision detection, and
  persisted in the v4 memory image (v3 images are rejected).
- `Transfer` reads the sem and refuses lessons without one; `parseLessonLabel` survives
  only to validate legacy (pre-sem) packs and to refuse a semantic-looking display label
  that contradicts a verified sem (display-spoof guard).
- Import validation is sem-first at every entry point (all pack ingress funnels through
  `apply_pack` events); `nvsa-verify -pack` re-derives rulegarden-domain sems and reports
  forged, foreign-domain, and legacy entries distinctly.

Forgery matrix covered by tests (`TestApplyPackRejectsForgedLabel`,
`TestSemPackSignAndTamper`): forged sem, spoofed label beside a valid sem, sem stripped
from a signed v2 pack, sem injected into a signed v1 pack, legacy label forgery.
